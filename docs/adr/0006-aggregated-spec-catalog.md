# ADR 0006 规格目录聚合：用户看到的是“服务”，服务商只是履约渠道

- 状态：已采纳（2026-11-19）

## 背景
用户（产品负责人）要求：把所有已对接服务商的全部规格都展示给用户，用户先选城市、再选规格；提交时再决定由哪家服务商的哪个规格来办。这样聚合平台才有意义：某一家缺某个规格，不应该导致用户看不到它。

T019 的同步按“服务商”建规格：每家各建一份本地规格（`zy_622`、`qwy_622`），新规格默认下架、映射停用、没有路由规则。结果是重复、且默认不可见。

## 决定
1. **本地规格（`specs`）= 面向用户的一项服务**，与服务商无关；`provider_specs` 是“哪家能办、对方编号是什么”，一个规格可以有多家映射。
2. **同步时跨服务商合并**：
   - 同一 `upstream_group` 的服务商共用编号（实测鹧应和黔微云 774 条编号和内容完全一致），按 `(upstream_group, provider_item_id)` 合并到同一规格；
   - 不同上游按“规范化名称 + 像素宽高”匹配；匹配不上才新建；
   - 新建规格编码不再带服务商前缀，用 `cat_<上游或服务商>_<编号>`。
3. **同步进来默认可用**（可在同步时关闭）：规格上架、映射启用、自动建一条该服务商的路由规则；运营之后手动改过的状态、启用、优先级，再次同步不会覆盖。
4. **地区从名称识别**：按 `app/data/regions.json` 把“广州市社保证”“贵州身份证”识别为市级/省级地区码，写入 `specs.region_code`；识别不出视为全国通用（为空）。
5. **用户端按城市过滤**：选了城市后，展示“全国通用 + 本省 + 本市”的规格；提供有地区专属规格的城市列表给小程序做城市选择。
6. **路由在提交时决定**：沿用 `route_rules` 按优先级选择启用中的服务商；同一规格多家可办时自动互为备选（同一上游不互为备份的规则不变）。

## 理由
用户关心“能不能办我这个城市的这个证”，不关心哪家服务商。把服务和渠道分开，新接一家服务商只会增加覆盖和备选，不会增加重复条目。

## 代价
- 名称识别地区是启发式的，会有误判，需要后台能手动改地区码。
- 默认上架意味着服务商目录里的条目不经人工审核就对用户可见；运营可关闭“同步后自动上架”，或事后下架。
- 成本（`cost_fen`）同步时未知，默认 0，需要运营补。
